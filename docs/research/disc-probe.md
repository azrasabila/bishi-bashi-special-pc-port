## Black-area diagnosis — 2026-10-21

A bounded Xvfb run showed a game thread at roughly 94% CPU while the window/presentation thread was mostly waiting (`.local/probe/black-sample/threads.log`). **Throwaway probes inserted only into ignored generated C#** then localized the stall: boot returns from the repaired pad initializer and enters `func_80015A2C`; its initial CD queue request succeeds (`0x80032240`), it issues a `DsPacket` command, and its completion flag remains `0x12` over more than 67 million polls in six seconds (`.local/probe/black-probe.log`). The screenshot remained black with only RecompOne's own menu. These observations do not establish any rendered game content.

Static code-flow explanation: `func_80015A2C` loops at original address `0x80015B08`, repeatedly calling `VSync(1)` and reading CD status without progressing while bit `0x10` remains set. RecompOne's `LibEtc.VSync` returns early for mode 1 without `Runtime.PresentFrame`; `Runtime.PresentFrame` is the only caller of `LibCd.Tick`, which runs `LibDs.Tick`/`Pump` to drain queued `DsPacket` jobs. `Interrupts.PollSlow` and the host's `PresentLoop` do not pump this queue. The combination strongly explains the perpetual in-progress CD status and black area: a CD operation cannot complete when game code only *queries* VSync. This is an inference from code plus the repeated status observation, **not** evidence that textures or the original disc data are wrong. The bounded probes did not patch the queue or verify any minigame.

Next fix should advance CD jobs independently of a `VSync(0)`/present-frame call while retaining frame-timed delivery; verify the flag clears and boot moves beyond `func_80015A2C` before changing rendering or assets. Do not force the flag in game memory or treat the black screenshot alone as a GPU defect.

### CD read and byte trace (follow-up)

A bounded run with temporary probes **only in ignored generated C# and the local RecompOne checkout** captured `.local/probe/sector-trace/step.log`. The game requests LBA **62762** (descriptor at `0x80026E5C`, target `0x801413BC`, 0x5000 bytes) with mode `0xA0`, and calls `CdGetSector` with 512 words (2048 bytes) per sector. The ten observed transfers use **62762, 62764, …, 62780** rather than the consecutive **62762–62771**. The first transfer copied `13 58 62 02 00 00 08 00 00 00 08 00 50 48 00 00 …`, which exactly matches original raw sector 62762 **starting at byte 12**; its 2048-byte user payload starts at byte **24** with `50 48 00 00 …`. Direct reads of the ignored BIN independently match both observations. `CueBinImage.ReadSectorData(lba, 2340)` chooses byte offset 12, and `LibCd.CdGetSector` copies from FIFO offset 0 in mode `0xA0`.

The skipped-sector cause is confirmed at both boundaries in the same trace: `LibDs.Feed` calls `LibCd.Step(1)` (62762 → 62763), then `LibCd.CdGetSector` also calls `AdvancePos(1)` under `_readActive && _cbReady == 0 && _cbData == 0` (62763 → 62764). This double advancement also occurs on the earlier read at LBAs 5472, 5474, …; it is not peculiar to MENU.BIN. Disc inventory places 62762–62771 in the final ten sectors of `MENU.BIN` (extent 62713–62771); 62772 is `SYSTEM.CNF`, and 62773 onward is `DMY.`. Thus this transfer demonstrably crosses into other files.

The 24-byte offset matters independently: the inflater interprets the **copied sector header** bytes `13 58 62` as a little-endian length `0x625813` (6,445,075). The actual first four *user-data* bytes are `50 48 00 00` = `0x4850` (18,512). At LBA 62762, `MENU.BIN` has exactly 18,516 bytes remaining (`118868 - (62762 - 62713) × 2048`), i.e. that 4-byte length plus 18,512 bytes. This strongly corroborates that the game expected a contiguous 2048-byte user-data transfer, not the returned raw-header slice. **The inflater has not been changed**. The root problem is upstream in the `LibDs`/`LibCd` sector advancement and payload selection; mode-specific API semantics and any correction still require a bounded regression check before changing the shared runtime or a game hook.
